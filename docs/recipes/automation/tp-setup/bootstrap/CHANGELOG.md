## [1.7.92-auto-on-prem-jammy]
### Fixed
- [PCP-24359] **The app-build name matcher treated a dotted sibling as a duplicate, and the image gate never pinned the tag it was vetting** (`page_object/po_dp_flogo.py`, `.github/scripts/check-automation-image-tag.py`, `.github/workflows/docker-image-ghcr-build-push-public.yml`). Five items deferred out of PCP-24348's review rounds, all recorded there as remaining windows rather than claimed away. Two of them turned on questions about the live CP, so those were **answered against a live CP (1.21) before any code was written** — and one of the two came back the opposite way from how it was filed.
  - **The name matcher excluded word characters and hyphens after the name, but not a dot.** `app_build_name_pattern()` ended with `(?![\w-])`, so `rest-flogo-1` — the project default — also matched a `rest-flogo-1.2` row. Same class as the `-1` vs `-10` bug PCP-24348 fixed, one character over, and deliberately **not** fixed there: PCP-24348 left the end of the name unanchored on the strength of PCP-23953 (a both-ends anchor on an unverifiable rendering that had to be walked back), so narrowing that end again needed evidence, not a one-click edit.
  - **The evidence: yes, a Flogo app build name can contain a dot.** Verified end-to-end on a real Data Plane rather than argued from the regex. An app whose Flogo JSON `name` is `rest-flogo-1.2` uploads cleanly; the wizard's `#build-name` field accepts it with no `pattern`, no `maxlength` and `checkValidity() == true`; the build is created; and the App Builds table renders `rest-flogo-1.2` verbatim — **above** `rest-flogo-1`. So this was a live path, not an unreachable one: against the real two-row table the shipped matcher selected **2** rows and the fixed one selects **1**. Because the dotted row sorted first, the `count()` guard reported a duplicate that did not exist **and** `.first` would have handed `flogo_app_deploy` the wrong build to deploy. The probe build was deleted afterwards. Fixed by widening the boundary to `(?![\w.-])`; every rendering the matcher is known to accept continues with a space or end-of-string, never a dot, so nothing it used to match stops matching.
  - **Selecting a duplicate by build status: dropped, because there is no status to select on.** PCP-24348's review asked for `.first` to be replaced by "prefer a build in a successful/terminal state", and that was deferred precisely because nobody had verified such a selector existed. It does not. On the live capability page the table is `Name | ID | Created By | Created | Tags | Included Connectors | actions`; no column carries a state, no header is sortable, a DOM-wide search for a status-bearing element inside the table returns nothing, and the row action menu is `Check Usage / Deploy / Export Flogo File / Export App Build`. The payload the table renders — `{buildId, name, createdBy, createdDate, connectorsUsed, flogoBaseVersion, nonDPBuild}` — has no status field either. **A Flogo app build is not a stateful object once listed; it is listed because it was created.** So the premise was wrong, and the wrong-build-deployed consequence the item described turned out to be reachable through the *matcher* instead — which is fixed above. Ordering is left alone rather than replaced with a guess: on a true duplicate both rows are the same app built from the same uploaded file, and the only remaining discriminator is the `Created` cell, so picking "newest" would mean parsing a locale-formatted date (it renders with a U+202F narrow no-break space) to choose between two equivalent builds. That buys nothing and adds a locale-dependent failure mode. The finding is recorded in `app_build_rows()` so the next reader does not re-open it.
  - **The gate resolved the tag three times and pinned none of them.** `manifest_exists()` resolved it, `image_revision()` resolved it again, and the deploy resolves the same mutable tag later still — so nothing tied the bytes that passed PARITY to the bytes anyone would pull. `manifest_exists()` now returns the registry's `Docker-Content-Digest` alongside the verdict, parity is asked about **that digest** rather than the tag, and the digest is printed as a greppable `IMAGE_DIGEST=sha256:…` line **and** written to `$GITHUB_OUTPUT` as `image_digest` (addressable as `steps.image-tag-gate.outputs.image_digest`). No consumer reads it yet — wiring a deploy or a chart bump to pin the vetted bytes is a follow-up — but the value is exported rather than only logged, so that follow-up does not have to scrape a job log. A registry that omits the header reports `IMAGE_DIGEST=UNKNOWN` and does not block — "could not pin" follows the same warn-don't-block rule as an outage, and is reported rather than silently passing so it cannot be mistaken for a successful pin. A malformed digest is dropped rather than pinned, since it is fed back into a v2 URL path.
  - **The run now re-asserts, at the end, that the tag still points where it did at the start.** Closes the window *inside* the run: without it a manifest could be replaced mid-check and every verdict above would describe an artifact nobody will ever pull. A tag that **moved** fails; a tag that was **deleted** (a definitive 404) also fails — the opening probe already treats the identical 404 as a hard FAIL, so downgrading it to a warning just because it arrived second would be inconsistent. Only a genuinely inconclusive answer (outage, or a 200 with no usable digest header) warns and passes. Deliberately **not** a full guarantee, and this entry does not claim one — it cannot see a replacement that lands after the check returns. Only the build workflow refusing to overwrite can do that, which is why the next item exists.
  - **The build workflow refuses to republish an existing tag unless explicitly forced.** This is the sharpest of the deferred items, because PCP-24348 is its own case study: that ticket argued — correctly — that rebuilding `1.7.90` under the same name was not an option, since a chart pinned it and already-pulled digests would not update. Yet the remedy applied **twice** during its own review rounds was exactly an in-place rebuild of an already-published `1.7.91`. The gate structurally cannot see this, because it re-resolves the tag: PARITY becomes satisfiable by *mutating the artifact* instead of moving the version, and it verifies the tag as of now, not the tag as anyone else received it. A new `forceOverwrite` input defaults to **false** and the build fails with the digest of what is already published; overwriting is now a deliberate act. Three properties the first cut got wrong and review caught:
    - **It fails CLOSED.** `imagetools inspect` exits non-zero for a genuinely absent tag *and* for DNS/TLS/5xx/429/auth failures alike, so using it as a bare `if` made a registry blip read as "tag is free" — fail-open, and worst exactly when the registry is flaky, which is the likeliest reason someone re-dispatches a build. Only an explicit not-found now permits the publish; anything indeterminate stops the job.
    - **It is scoped to immutable tags.** `latest` is this workflow's default input *and* this repo's documented runtime image (`README.md`, `docs/design/README.md`, `dev/platform-provisioner.sh`'s `PIPELINE_DOCKER_IMAGE`), so it is meant to move. Guarding it would hard-fail every routine publish and train an automatic "just tick forceOverwrite" reflex — which would then be ticked on the automation tag too, defeating the point.
    - **The dispatch input reaches the script via `env:`, not `${{ }}`.** Actions substitutes before bash parses, so an inlined `tagName` containing a quote or `$(…)` would execute in a runner holding the registry push credential.
    - Still **not atomic**, and the step says so rather than implying otherwise: the push happens minutes later, so two concurrent dispatches can both pass. Closing that needs immutable tags on the GHCR package or a per-tag concurrency group; this stops the far commoner single-operator case.
  - **The build records which commit it published.** Nothing interlocks a `workflow_dispatch` against another commit landing after it, and on PR #443 the rebuild was dispatched at 20:43:11Z with the next commit landing at 20:44:58Z — recoverable only because that commit touched `CHANGELOG.md`, which the carve-out forgives. A runtime file would have meant a third build. Ordering cannot be fixed from inside the build (the race is with a push to the branch), so the outcome is made **answerable** instead: a job summary naming the tags, the built-from commit, the branch and the Dockerfile, so "is the published tag current?" takes one glance rather than a gate re-run. The overwrite guard removes the other half of the hazard, since a second build under the same name is no longer something a re-dispatch does silently.
  - **The duplicate anonymous-token fetch was NOT collapsed — the attempt was reverted.** Fetching one token in `main()` and threading it looked free, and was not: it put a **live ghcr.io request into ~9 unit tests** that mock every registry helper and were hermetic before (reproduced — one real request per test, i.e. a 30s connect timeout each on a runner with no egress), silently walking back what `tests/conftest.py` exists to guarantee. Memoising in a module global is worse still: the gate's tests share one module instance, so a cache makes them order-dependent *and* pins a transient failure for the rest of the run. So the run makes a few trivial token round trips instead — the same trade PCP-24348 accepted when it declined this ("two round trips on a job that runs in 9s"), and item 2's real content (pinning the tag to a digest) never depended on it. A test now pins that `main()` makes **no** network call when the registry helpers are mocked, so this cannot regress silently.
  - **Still open, deliberately.** PARITY proves *which source tree*, not *which Dockerfile* — `dockerfileName` is a free `workflow_dispatch` input, so building the right commit with `Dockerfile-on-prem` passes all three checks. Closing that wants a `com.tibco.dockerfile` label the gate asserts, and is out of scope here.
  - **Cross-review (Opus 4.8 + Haiku 4.5 + GPT-5.6-terra) before commit changed the shipped result.** All three independently found the fail-open overwrite guard; Opus additionally found the `latest` breakage and the hermeticity regression, both of which were **reproduced before being believed** (a scripted probe showed one real ghcr.io request escaping per mocked test; `grep` confirmed `:latest` in `dev/platform-provisioner.sh` and two READMEs). Two reviewers also observed that the new workflow tests were substring greps that the fail-open satisfied — so the guard now has a **shell-level test** that runs the real step body against a stubbed `docker` distinguishing found / not-found / network-error. Every fix carries an A/B: reverting the guard turns the registry-error test red while the two substring tests stay green; restoring the eager token turns the hermeticity test red; collapsing the deleted-tag branch turns that test red while the inconclusive one stays green; and handing the re-assert a digest instead of the tag turns the new spy test red **while the pre-existing move test stays green** — which is precisely why that spy was added.
  - Tests: 6 on the matcher (4 rejection cases, the live two-row table reproduction, and one pinning that the widened boundary did not narrow the accepted renderings), 10 on the gate's digest pinning / re-assert / hermeticity, and 6 on the workflow guard (4 executing its real shell). ## [1.7.91-auto-on-prem-jammy]
### Fixed
- [PCP-24348] **The Flogo app-build step could not survive the state its own retry created, and CI could not tell a published image from a current one** (`page_object/po_dp_flogo.py`, `.github/scripts/check-automation-image-tag.py`). Two defects filed together because the remedy for the first *is* the version bump the second forces — splitting them would mean two bumps, two image builds, and two chances to recreate the same drift.
  - **Defect B — the retry created a duplicate build, then broke on it forever.** `deploy-flogo` timed out after 30s waiting for `.finish-container .step-description` to show `Creating new app build...`; the retry created a **second** app build with the same name, and every retry after that failed deterministically at the same line:
    ```
    Locator.is_visible: Error: strict mode violation:
    locator(".app-build-container td:first-child").filter(has_text="rest-flogo-1")
    resolved to 2 elements
    ```
    Retries 2 through 5 failed identically, the run had to be killed after 7, and `deploy-bwce`, `deploy-bw5ce`, `create-bmdp`, `deploy-ems` and `dp_config_ems` were all blocked behind it. Confirmed in the CP UI — two builds 22 seconds apart — and one manual deletion later the next run passed `deploy-flogo` with zero retries.
  - **The line that raised is the one that exists to prevent this.** Not a side effect: it is the *"is a build already there? then skip creating one"* guard. Because it asked with an un-narrowed `is_visible()`, two rows made it **raise instead of answer** — so the check that would have short-circuited the retry into a success was the very thing that failed it. That is why the run never self-healed. All three readers of the table (the guard, the deploy poll, the action-menu clicks) now go through one `app_build_rows()` helper that is deliberately **not** narrowed, so a caller asking "does one exist?" narrows with `.first` while the duplicate check can still take a real `count()`. It filters on the **name cell** rather than the whole row, so a build id or a date column cannot satisfy the match.
  - **The name is matched with an anchored pattern, not a bare substring.** `has_text` is a case-insensitive **substring** match, and the pre-fix code leaned on it. Left as-is, the new `count()`-based duplicate check would have made that *worse* than what it replaced: on a Data Plane also holding `rest-flogo-10`, `rest-flogo-1` — the project default app name — would report a duplicate that does not exist, claim a build that was never created, and let `.first` deploy the **wrong** build. `app_build_name_pattern()` anchors at the start and refuses to let the next character continue the name. It is deliberately **not** anchored at the end: PCP-23953 had to walk back exactly that kind of both-ends anchor after it turned an unverifiable `<name> (<id>)` rendering into a failed deploy on a path nobody could test. So `rest-flogo-1 (9b16a21f)` still matches while `rest-flogo-10`, `rest-flogo-12`, `rest-flogo-1-backup` and `my-rest-flogo-1` do not.
  - **A duplicate is now recovered from *and* reported.** Recovering is not the same as being fine: the extra build is real, it stays in the CP UI, and only a retry can have produced it. The step warns with a screenshot and the row count instead of leaving it to be discovered later. Which of the duplicates the deploy then acts on is `.first` — enough to get past the step, but not a decision this code makes, which is why it is reported rather than swallowed.
  - **One of the triggers is gone, so this particular race cannot start the cycle again.** `Creating new app build...` is a **transient progress line**, not a state. Gating on it meant a build that reached the terminal state before the check ran threw a bare 30s Playwright timeout — reporting a build that had **succeeded** as a failure, which is what sent the retry off to create the second one. Only `Successfully created app build` is worth gating on, and it was already polled (`check_dom_visibility`, 300s) on the very next line, now with a screenshot on the way out instead of an uncaught timeout. **This does not make creation atomically idempotent**, and the CHANGELOG should not claim it does: the guard still polls for only ~13s (`refresh_until_success`, 3 refreshes) before creating, so a build submitted by a previous attempt that has not yet surfaced in the list can still be duplicated, and every other exit path inside the upload wizard can still leave a submitted build behind. What is true is the weaker and still valuable claim — **a duplicate is now survivable and reported instead of terminal**. The remaining bare `wait_for()`s in the wizard are rule-#5 violations worth their own ticket.
  - **Time-to-failure for a genuinely stuck build goes 30s → 300s per attempt.** Honest trade, not a hidden one. An API-level rejection is unaffected — `wait_for_success_message(page, 5)` still catches `.pl-notification--error` and exits within 5s, one line earlier. What is slower is the case where the create phase silently never starts, which the old 30s wait did surface. Detection did not get weaker (the old path raised an uncaught, screenshot-less Playwright timeout; the new one ends in a logged poll plus `Util.exit_error` with a screenshot) — it got later.
  - **Defect A — the published `1.7.90` image predated the PCP-24310 merge by 33 minutes, and both CI checks passed.** The image was pushed at 19:04:48Z; the merge commit that also set `version.txt` to `1.7.90` landed at 19:37:59Z. The five declared sites agreed on `1.7.90` (DRIFT ✓) and the manifest existed (PUBLISHED ✓) — **neither check ties the artifact back to the source**, so an image missing the final review revision shipped under the tag that claimed to be it. No source fix is needed for A itself: `main` is already correct, and rebuilding under the existing tag is not an option because chart `1.20.7` pins it and already-pulled digests would not update. The bump to `1.7.91` is what clears it.
  - **Third check: PARITY — the manifest must have been built from this source tree.** The build workflow already stamps `org.opencontainers.image.revision`, so the gate now walks index → **every runnable** platform manifest → config blob, reads the commit each was built from, and compares `git rev-parse <rev>:<bootstrap dir>` against the same tree at the PR head. **Tree hash, not commit identity or timestamps** — content-addressing is what survives the rebases and squash merges that would otherwise make this cry wolf, and the compared directory is exactly the Docker build context (`COPY . .`, and everything `.dockerignore` drops is git-ignored anyway).
  - **It compares the PR HEAD, never the checkout's `HEAD`.** On a `pull_request` run `actions/checkout` gives `refs/pull/N/merge`, so `HEAD` is base ⊕ this PR. Comparing against that would fail the gate the moment *somebody else's* bootstrap change merged to `main` — with a message naming **their** files and a remedy (rebuild this branch) that cannot possibly fix it. The job now passes `PR_HEAD_SHA: ${{ github.event.pull_request.head.sha }}` and the script prefers it (`--head` for local runs). With no head ref — a push to `main` — parity is a **no-op**: a squashed commit can never match an image built before that commit existed, so leaving it on would have meant an unfixable red `main` after two back-to-back bootstrap merges. Parity is a pre-merge check and now says so.
  - **All platforms, not just the first.** The build is `linux/amd64,linux/arm64`. Reading only the first child manifest would let a stale arm64 ship behind a green check, so every non-attestation child is read and a disagreement is a **FAIL**, not an inconclusive warn — the registry answered fine; the artifact really is inconsistent.
  - **Registry metadata is treated as untrusted.** The revision label and the index digests reach `git` and a v2 URL path as bare arguments. `subprocess(shell=False)` stops shell injection but not **option** injection — a label of `--upload-pack=…` would be parsed by git as a flag — so the label must match `[0-9a-f]{40}` and digests `sha256:[0-9a-f]{64}` before either is used. Copilot's review pointed out the head ref reaches git the same way; it is CI/operator-supplied rather than registry-supplied and `--head HEAD` is legitimate, so it is not held to a bare sha, but a leading `-` is now refused.
  - **Verified live against the real registry, in both directions.** Run on `1.7.90` from a checkout at the merge commit, the new check reproduces defect A and names the file the ticket named:
    ```
    FAIL: ...:1.7.90-auto-on-prem-jammy does NOT contain this source.
          the image was built from 394a81254c19; .../bootstrap has changed since:
      .../page_object/po_bmdp_config.py
      .../tests/test_cp121_ems_registration.py
    ```
    `394a8125` is 2026-09-08T18:33:54Z — an hour before the merge. Re-verified after the review round below, now reading **both** platform manifests: they agree on `394a8125`, parity against that same commit returns `True`, and against the branch tip it still names `po_bmdp_config.py`.
  - **Inconclusive still warns, and non-runtime drift does not block.** A missing label (older images), a force-pushed and now-unreachable revision, or a registry hiccup warn rather than fail, matching the rule the gate was built on — with a machine-greppable `PARITY=OK|FAIL|INCONCLUSIVE` line so a *permanent* warn is detectable instead of being mistaken for a pass. That fail-open is a deliberate limit, not an oversight: this gate is a pre-merge net, and blocking every PR on a GHCR hiccup is worse than the drift it prevents.
  - **The carve-out includes `tests/` and `e2e/`, because otherwise this gate quietly changes policy.** Everything under `bootstrap/` ships in the image, so a *pure unit-test* addition would have forced a version bump, four recipe edits, a chart bump and a hand-triggered `workflow_dispatch` build. Test directories cannot change what the running server does, so they warn alongside the four top-level docs (`CHANGELOG.md` / `README.md` / `CLAUDE.md` / `DESCRIPTION.md`). The **exact** set is top-level only — `page_object/README.md` still blocks, so a renamed source file cannot slip through on a basename — and one runtime file among a hundred doc changes still blocks.

  - **Root cause — one resource, two naming conventions.** A Data Plane's storage resource is called `<dp_name>-storage` when **CLI mode** creates it (`cli_object/orchestrator.py:215`) or when it is provisioned with the Data Plane itself, and `ENV.TP_AUTO_STORAGE_CLASS` (`nfs`) when **GUI mode** creates it (`po_dp_config.dp_config_resources_storage`).
