## [1.7.82-auto-on-prem-jammy]
### Fixed
- [PCP-23553] **A CLI-mode deploy ended with three independent observability resource sets instead of one Global resource both data planes link to** (`page_cli.py`, `case/k8s_config_dp_o11y.py`, `case/bmdp_config_dp_o11y.py`, `charts/provisioner-config-local/recipes/tp-automation-o11y.yaml`). The contract a deploy must satisfy is: create the **Global** observability resource, then **switch** `k8s-auto-dp1` **and** `k8s-auto-bmdp1` to it. Measured on `ins-owen-tas-75` (chart `1.21.0-alpha.10-tas`), the run created the Global resource correctly, then created a **second, DP-local** set through the same UI wizard for `k8s-auto-dp1`, and a **third** set over REST for `k8s-auto-bmdp1` — `Switch dataplane ... to Global` appeared **0 times** in the whole pipeline log. The automation still recorded `o11yResources: true`, so the pipeline was green; only `a-gcp-doctor` Check #5 caught it (k8s DP = DP-LOCAL, bmdp = NO-RESRC). This had been fixed three times before and kept regressing, so the contract is now pinned in code and in tests.
  - **Root cause 1 — the previous fixes all landed on a path production deploys do not take.** `9cb96ddd` (PR #80) replaced create-local with switch-to-global in the **browser** path (`page_dp.py`, `page_bmdp.py`), but every profile-driven deploy sets `GUI_TP_AUTO_USE_CLI: true` and routes to `page_cli.py`, added later by PCP-19413 (PR #333) as a parallel implementation. Its own comment said it mirrored `case/k8s_config_dp_o11y.py` — the ancestor PR #80 never fixed — so it inherited the pre-fix `if TP_AUTO_DATA_PLANE_O11Y_SYSTEM_CONFIG: switch else: create` shape. That env var defaults `false` (`utils/env.py:305`) and **no recipe exposes a GUI key for it** (zero hits for `O11Y_SYSTEM_CONFIG` across all `*.yaml`), so the switch branch was unreachable dead code in CLI mode and every deploy took the create-local `else`.
  - **Root cause 2 — the BMDP was outside the guard entirely.** `_run_api_bmdp_config` called `OllyApi(client).create_o11y_resources(bmdp_name)` with no `O11Y_CONFIG_VIA_UI` check at all, so it always took the very REST path PCP-22010 had declared unusable.
  - **Root cause 3 — the API cannot satisfy the contract for a data plane at all.** `OllyApi` exposes only `create_o11y_resources(target)`; there is **no switch/link-to-global operation anywhere on the API side**. So the API branch could only ever create a second resource set — the silent degradation above — and "fall back to the API" is not a valid fallback for a data plane.
  - **Fix — one contract, one code path per subject.** `_run_gui_o11y` now routes **Global → `o11y_config_dataplane_resource`** (a create, which is correct for Global) and **any data plane → `o11y_config_switch_to_global`**, and the unreachable `TP_AUTO_DATA_PLANE_O11Y_SYSTEM_CONFIG` branch is gone from the CLI routing (the env var itself stays — `po_dp_config.o11y_config_dataplane_resource` still reads it for its Metrics/Traces step-skip logic, and the Hub UI and MCP tools still expose it). It grew an `is_bmdp` argument that selects `PageObjectBMDPConfiguration`, so the BMDP now goes through the same UI switch as the k8s DP instead of REST. Both switch helpers self-navigate (data plane list → DP → Configuration → Observability), so the old `goto_dataplane` + `goto_dataplane_config` prelude — and with it the `PageObjectDataPlane` import — is no longer needed.
  - **The two data-plane API branches are kept, but now fail loudly.** They are retained (not deleted) so the structure is ready when the API gains switch-to-global, but both now go through `_assert_dataplane_o11y_via_ui()`, which raises `NotImplementedError` naming this ticket rather than falling back to create-local — otherwise flipping the constant later silently reproduces this exact bug. The guard is raised **outside** each `try`, so a misconfigured path aborts the DP/BMDP thread instead of being swallowed as one more recoverable o11y warning. The **Global** API branch is correct (it is a create, not a link) and stays functional.
  - **`O11Y_CONFIG_VIA_UI` is documented as permanent, not temporary.** PCP-22010 introduced it as a `TEMPORARY` constant whose comment told the next maintainer to delete it once the API was fixed — the opposite of the intended design. It is a code constant **by design**: deliberately not a recipe/guiEnv key or env var, so it cannot be misconfigured from the provisioner UI. It answers **HOW** o11y is configured; `GUI_TP_AUTO_ENABLE_CONFIG_O11Y` answers **WHETHER** to configure it at all.
  - **The two standalone cases are aligned with the same contract**, so the next path copied from them does not reintroduce the bug a fourth time — which is exactly how it was reintroduced the third time.
  - **Recipe round trip collapsed.** `tp-automation-o11y.yaml` defined `TP_AUTO_ENABLE_CONFIG_O11Y` (default `true`), then `TP_AUTO_IS_CONFIG_O11Y` from the same guiEnv key with a **contradictory** `false` default, then re-exported the first over the second inside the `cli-full-automation` task. `TP_AUTO_ENABLE_CONFIG_O11Y` was referenced by nothing else — no `condition:`, no other task — so the three lines collapse to the one global `TP_AUTO_IS_CONFIG_O11Y: ${GUI_TP_AUTO_ENABLE_CONFIG_O11Y:-true}`, carrying the contract in its comment.
  - **Cross-review follow-up 1 — a wizard that failed is no longer reported as success.** Raised independently by **all three** reviewers (Opus 4.8, Haiku 4.5, and the cross-family GPT), each at HIGH. Neither wizard raises when it fails: `switch_to_global_config()` warns when the post-link `View in Global Configuration` check fails, and `o11y_config_dataplane_resource()` warns + cancels on a `.pl-notification--error`. Both then simply return, so `_run_gui_o11y` returned `True` on an unlinked data plane — or an uncreated Global resource — and the caller wrote `o11yResources: true`. That is the *silent-green* half of this very ticket ("the automation still recorded `o11yResources: true`, so the pipeline was green"), one abstraction layer below where the routing fix stopped, and worse than a plain miss: the recorded key short-circuits every later run as "already configured, skipping". New `_assert_o11y_recorded()` keys each subject on the report key its own wizard writes **only** on a confirmed success — `o11yConfig` for Global, `switchGlobal` for a data plane — and raises when it is absent. Cheap and precise: it reuses existing, already-trustworthy signals instead of adding new plumbing. Verified before acting — both `set_dataplane_info(..., "switchGlobal", True)` call sites (`po_dataplane.py:1182,1209`) and the `o11yConfig` write in `po_dp_config.py` all sit past their respective failure branches.
  - **Cross-review follow-up 2 — a failed Global creation now aborts the bootstrap, and the process exits non-zero.** `_run_api_steps` discarded `_run_gui_o11y`'s return value, so a Global resource that failed to assemble let the run proceed straight into switching both data planes to a resource that does not exist — guaranteeing this ticket's failure mode from the other direction. It now raises. **Copilot review then caught that raising alone was not enough:** `run()` caught the bootstrap exception and `return`ed, exiting **0** — turning "silently continue with a missing Global" into "silently abort with a missing Global", still a green pipeline. It now `sys.exit(1)`, matching the `errors` branch at the end of the same function. A bootstrap failure means no OAuth token and/or no Global resource, so no data plane is created either way and the run has nothing to report green about. (The sibling `TibcopCLI.from_env()` failure two lines below still `return`s; pre-existing and untouched.)
  - **Human-review follow-ups (adhanshe-tibco, APPROVED 8.0/10 — all four findings verified against the code before acting).** (1) The source-level guard swept a **hardcoded four-file list**, so a *fifth* path added later — which is precisely regression #4 — would be invisible unless whoever adds it also remembers to extend the list, and the premise of the guard is that they will not. Same vacuous-pass shape as the per-line regex it had already replaced, one level further out. It now sweeps **every** module under the bootstrap tree (`rglob`), with `tests/` excluded (test modules drive the wizard directly — that IS their subject) and a one-entry, commented allowlist for `page_cli.py` (whose `dp_name` argument sits inside the `== TP_AUTO_DP_NAME_GLOBAL` branch and is pinned behaviourally instead). It also asserts **non-vacuity** — a sweep that suddenly sees fewer than 3 call sites fails rather than passing while checking nothing. (2) `o11y_config_switch_to_global` had **no `TP_AUTO_IS_CONFIG_O11Y` guard**, unlike the `o11y_config_dataplane_resource` it replaces: running `case/{k8s,bmdp}_config_dp_o11y.py` directly with the flag off used to be a no-op and would have started performing the switch. The guard now sits **inside both page objects**, beside its sibling, rather than being every caller's job — which is also what the WHETHER/HOW split in this ticket implies. (The `page_cli.py` entry points were never affected; all three gate on the flag before calling in.) (3) A data plane that fails to link still exits the pipeline **0** — reviewed and **deliberately left non-fatal**: a missing *Global* resource voids the whole deploy (hence fatal), whereas one DP failing to link is a localised gap on an otherwise working deploy, and non-fatal is the pre-existing behaviour. The half this ticket does fix is the lying report — `o11yResources` is written only on success, so a failed link is no longer recorded as configured and no longer short-circuits the next run. The `except` now says all of this so it reads as a decision, not an oversight. (4) The BMDP o11y step is no longer browser-free (see the performance note below) — flagged as a note, not a change request.
  - **Performance cost, stated explicitly:** the BMDP o11y step goes from a single REST call to a full browser launch + login + wizard + logout, and `_gui_lock` serializes it against the k8s DP's session rather than overlapping them — a third serial browser session on the critical path of a deploy that already carries a GUI EMS step through the same lock. This is the correct trade (the API genuinely cannot link a data plane, so there is no cheaper *correct* option), but it is a real wall-clock cost and belongs on the record for whoever next looks at deploy duration.
  - **Known, deliberately not fixed here:** `ReportYaml` has no internal locking (each write is a separate `yq -i` read-modify-write), so a page-object write from one thread can still race a `report_lock`-held write from the other. Pre-existing and repo-wide — the k8s DP path already did unlocked page-object writes from its own thread, and `_gui_lock` serializes the two `_run_gui_o11y` calls against each other. Fixing it properly means locking inside `ReportYaml`, which is outside this ticket. Also flagged by the cross-family reviewer.
  - **Tests — `tests/test_po_cli_o11y_via_ui.py` rewritten around the outcome, 23 cases.** They assert what each subject *ends up doing* (Global creates; k8s DP and BMDP each switch, the BMDP through the BMDP page object), that each CLI entry point reaches the UI path, that both data-plane API branches raise `NotImplementedError` without calling `create_o11y_resources`, that the Global API branch still works, and that `O11Y_CONFIG_VIA_UI` is `True`. The regression guard is the **negative** assertion — parametrized over every non-Global subject, `o11y_config_dataplane_resource` is never called — plus a source-level sweep of every module under the bootstrap tree asserting any call site passes the literal `ENV.TP_AUTO_DP_NAME_GLOBAL`. Every previous fix failed because a newly added path called that method again, so it is guarded both behaviourally and at source. That source guard **parses** the file rather than regexing it line by line: cross-review pointed out that a per-line pattern silently matches nothing once a call is wrapped across lines (by a formatter or a long argument), so the guard meant to catch regression #4 would have passed vacuously — exactly the failure mode it exists to prevent, one level up. `ast.walk` ignores formatting and comments for free. Six further cases cover the review follow-ups above (an unconfirmed switch returns failure for both DP kinds, neither entry point records `o11yResources` when it does, a failed Global aborts the bootstrap, and `run()` exits 1 without proceeding). **A/B against the unfixed code: 11 of the original 17 fail**, including all six negative-guard cases and both API-branch cases; **A/B against the un-guarded follow-ups: 3 of the 5 cross-review cases fail** (the other two assert entry-point wiring that was already correct). Full bootstrap suite **627 passed, 1 skipped** post-change (baseline 621).

## [1.7.81-auto-on-prem-jammy]
### Fixed
- [PCP-23459] **The `Start <capability> App` toggle was inert on a resumed CLI run, and one direction re-created the exact warning PCP-23440 removed** (`cli_object/orchestrator.py`). Follow-up to PCP-23440 (PR #421), covering the three edges review surfaced there and that were scoped out on the grounds that changing the mechanism would have invalidated that PR's real-machine verification.
  - **Problem 1 — the two halves disagreed on any run against an existing report.** `_deploy_worker` returned at its `ReportYaml` **status** short-circuit, setting `results[key] = True`, *before* the toggle was read; `select_endpoint_test_tasks` read `start_enabled` **outside** that short-circuit, straight from the live env. **OFF then ON** was the damaging direction: nothing re-deployed the app, so it stayed at `replicas: 0`, yet phase 3 selected it. `_wait_and_test_worker`'s own skip needs **both** `endpointPublic` and `testedEndpoint`, which are only written inside the endpoint-test success branch and so had never been set — `wait_for_app_pods` therefore burned its full 120 s and logged `App pods not ready, skipping endpoint test`, precisely the misleading warning PCP-23440 set out to remove, on the one path where the user had explicitly asked for the app to run. It did not converge: every subsequent run paid it again, and the warning that would have named the cause was unreachable because the function had already returned. **ON then OFF** was benign by comparison — the app kept running and the 2-core reclaim never happened. Reachable in normal operation: the report directory is host-bind-mounted (`tp-install-on-prem.sh:465` mounts `report` to `/tmp/auto/report`), so a second run on the same box takes this path.
  - **Fix 1 — converge instead of silently doing nothing.** `startEnabled` is now recorded in the report next to `status`, and the short-circuit fires **only when the last run deployed successfully AND with the same toggle**; anything else logs the reason and falls through to a real deploy. This is a deliberate behaviour change — the previous resume semantics matched GUI mode, which is why PCP-23440 left them alone. Convergence is one run, not an oscillation: after the re-deploy the report agrees with the toggle and the next run skips again.
  - **Fix 1a — an ABSENT `startEnabled` means unknown, and is not guessed.** Only a report written before this field existed lacks it, and such a report does not say which toggle produced it. Pre-PCP-23440 runs ignored the toggle and always deployed the app running — but **PCP-23440 itself shipped in 1.7.80 already honouring the toggle while never recording it**, so a 1.7.80 report can equally describe an app sitting at `replicas: 0`. Defaulting to `True` would skip a toggle-ON run against exactly that report and leave the app stopped — the reported defect, unfixed, on the newest reports of all. Defaulting to `False` would re-deploy the toggle-OFF case for nothing. So `recorded_start_enabled` returns `None` and the caller **re-deploys once to converge**. The cost is honest and bounded: upgrading from 1.7.80 pays **one** rebuild-and-redeploy per app on the first resumed run, after which `startEnabled` is recorded and every later run skips normally. (Caught in cross-review; the first cut of this change did default to `True`.)
  - **Fix 1c — the skip keys on a recorded OUTCOME, not on the platform's wording.** `status` holds whatever `_get_app_state` returned — an unbounded string from the platform, kept for a human reading the report. Matching failure words against it only moves the guess: `"Failure"` is the sole spelling this code writes, so a platform-reported `Failed`/`Error`/`CrashLoopBackOff` would read as a success and phase 3 would endpoint-test an app that never came up. A whitelist of healthy states is worse — an unrecognised-but-healthy state would re-deploy on **every** run and never converge, since the same state is written back each time. So each run now records its own verdict as `deploySucceeded`, next to `startEnabled`, and the short-circuit reads that. Nothing about the decision depends on CP's vocabulary any more. (Raised in review; the reviewer suggested widening the match to a small set of failure words and confirming the vocabulary on a live instance — recording the fact removes the need to know it at all.)
  - **Fix 1b — a recorded `status: Failure` is no longer treated as success.** `if app_status:` was truthy for `"Failure"` too, so a deploy that had FAILED was skipped on the next run **and** recorded `results[key] = True`. `select_endpoint_test_tasks` then selected that app for phase 3, which waited for pods of an app that had never been deployed and burned the full `wait_for_app_pods` timeout on it — the same symptom as Problem 1, reached from the other side. A failed deploy now retries and reports the retry's own outcome. Pre-existing, but it lives in the exact block this change rewrote, and both were flagged in cross-review.
  - **Problem 2 — user policy was persisted into a git-tracked shared payload.** `apply_start_toggle_to_deploy_config` wrote `replicas` **in place** into `upload/{bwce,bw5ce,flogo}-payload.json`, which are checked into the repo. Writing `buildId` there is existing house style, but `buildId` is a per-run artifact that is unconditionally overwritten, whereas `replicas` is policy read from an env var. The run-scoped copy is what makes this safe to do at all — it is derived fresh from the pristine payload every run, so the "and what value do we restore it to?" question that blocked this under PCP-23440 no longer exists. `autoscalingConfig` is left in place (inert once autoscaling is off, so the user's min/max survive), a payload without the key does not grow one, and starting an app never re-enables autoscaling — that would be guessing at a value the user never gave.

This also removes both mirror warning branches, which only existed to describe a half-applied in-place write.

- [PCP-23045] **`flogo-build-and-deploy` deployed before the build finished, so `deploy-app` always failed with `buildStatus: Queued`** (`cli_object/flogo.py`). **Root cause:** `flogo:create-build` is **asynchronous** — it returns as soon as the build is accepted, with `"status": "Queued"` — but `build_and_deploy_app` called `deploy_app` on the very next line (Step 4 → Step 5) with no wait. A deterministic race, not a flake.
  - **Fix:** new `TibcopFlogo.get_build_status()` (`flogo:get-build-status --build-id <id> --json --no-loop`) + `TibcopFlogo.wait_for_build()`, called between create-build and deploy-app. It polls every 10s up to 900s (the DataPlane's own budget: 600s queued + 300s building), **logs every attempt** so a stuck build shows progress in the pipeline log instead of a silent wait (CLAUDE.md rule #5), proceeds only on a terminal `Success`, and aborts with a clear error on `Failure`/timeout instead of deploying an unusable build. `--no-loop` is used deliberately so the timeout, interval and logging are owned by this code rather than by the CLI's internal loop.
  - **Failure paths hardened** (from a 3-model cross-review — Opus 4.8 + Haiku 4.5 + GPT-5.5 — all three raised the same first three):

## [1.7.68-auto-on-prem-jammy]
### Security
- [TPSEC-116] **`GET /cp_api` host-suffix / userinfo SSRF leaks the CP bearer token (finding f027)** in the automation bootstrap Flask server (`server.py`). **Root cause:** `call_cp_api` built `base_url = https://<cp-host>` (a bare host, **no trailing slash**) and concatenated the request-supplied `api_path` **raw** (`url = base_url + api_path`) with no validation, then curled the result **with a live CP cluster-admin bearer token** (`Authorization: Bearer …`, from the `automation/auto-token` k8s secret). Because the base ends at a bare host, an `api_path` that does not start with a single `/` rewrites the URL **authority**, so curl sends the bearer to an attacker host — e.g. `@evil.com/x` → `https://<cp-host>@evil.com/x` (`<cp-host>` becomes userinfo, authority = `evil.com`), or `.evil.com/x` → `https://<cp-host>.evil.com/x` (host suffix). Unauthenticated `GET`, reachable via the `automation.<domain>` Ingress when the component is deployed (`TP_AUTOMATION_INSTALL=true`). **Fix (scoped to `/cp_api`):**
  - Require `api_path` to be an **absolute path** — start with exactly one `/` (reject `//`) — which forces every attacker-controlled byte **after** the authority-terminating slash, so neither Python `urlsplit` nor curl can be steered to another host; then assert `urlsplit(url).netloc == urlsplit(base_url).netloc` as **defense in depth**. Any violation returns **400 before the token is fetched or any curl runs** (the token never leaves).
  - Moved `Helper.get_auto_token()` to **after** validation (no sensitive k8s-secret read for a request that will be rejected), and added a code comment that the **absence of `curl -L`/`--location` is deliberate** (following a CP-returned 3xx would bounce the bearer to an attacker host and re-open this SSRF).
  - Regression tests in `tests/test_server_cp_api_ssrf.py` (14 tests): every authority-rewrite vector (`@evil.com`, `.evil.com`, `//evil.com`, absolute URL, relative, empty) returns 400 and asserts `subprocess.Popen` is **never called** (token never leaves); a legitimate absolute path is proxied to the CP host with the bearer; and tricky-but-legit paths (`@` inside the path, query string, backslash, `%2F%2F`, `/..`) stay pinned to the CP host (guards against future over-tightening). Full unit suite green (283 passed / 1 pre-existing skip). Cross-reviewed by Opus 4.8 + Haiku 4.5 + GPT-5.5 (SSRF confirmed complete; no single-leading-slash bypass found). Real-machine verified via Docker `/cp_api` before/after (pre-fix leaks the bearer to the attacker authority; fix returns 400, curl never invoked).
  - **Scope:** tight to `/cp_api`. The sibling `/run-cli-script` license-upload SSRF is fixed separately in [TPSEC-166] (1.7.67); the server-wide "no auth on any route" root cause remains tracked on epic TPSEC-73; the pre-existing `-d api_data` (dict-not-str) write-path bug is unrelated to this SSRF and left untouched.
